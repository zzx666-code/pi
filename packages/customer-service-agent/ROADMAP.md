# 智能客服功能路线图

## 结论

当前项目已经具备“咨询 + 下单 + 退款 + 转人工”的演示闭环。下一阶段不应只继续增加查询工具，而应补齐三个能力：

1. **售后闭环**：物流查询、取消申请和工单进度（退款申请已完成，见 T5）。
2. **可信执行**：权限、确认、幂等、并发控制、降级和隐私保护。
3. **可评估运营**：自动评测、链路指标、人工坐席和知识运营。

推荐先完成一条可演示的纵向链路：**查看本人订单 → 查询物流 → 判断售后资格 → 创建退款申请 → 查询处理进度 → 必要时转人工**。

### 进度快照（2026-09-18）

- **已完成**：订单列表与订单查询、退款申请与进度查询（含撤销与确认门禁）、退款与工单的状态机领域模块、坐席工作台（接口 + 界面）、人工接管与交还、客户侧接管状态自动刷新、工单创建幂等（一个会话只有一张未关闭工单）、坐席操作审计。
- **部分完成**：并发控制（机制齐全但分散，会话级并发锁仍是进程内的 `Set`）、工单生命周期（三态可用，缺客户侧进度查询）、评测集（6 个场景，只校验工具选择）。
- **确认已补齐**：订单和退款都是两段式——模型只能写草稿，正式提交的接口要求客户 JWT，模型够不到。退款的草稿在 `refund_drafts`，确认路由是 `POST /refund-drafts/:id/confirm`。
- **未开始**：物流查询、取消申请、结构化转人工摘要、正式认证与角色权限、外部接口韧性、隐私与限流加固、知识引用与版本、可观测性指标、知识运营入口。
- **并发防护已在真机验证**：`test/integration/concurrency.test.ts` 对真实 MySQL 跑八个并发请求，覆盖订单提交、退款申请、工单认领与关闭、以及同一会话的重复转人工，并据此修掉了订单提交的死锁——原先八并发下会返回 7 个 HTTP 500。
- **坐席操作已入审计**：认领、回复和关闭各写两条记录（`started` + 终态），被拒绝的尝试同样留痕并带原因码，`desk_audit_logs` 可按工单、客户或工号追踪。
- **剩下的缺口**：确认令牌没有主体与过期绑定；重启后重放、跨客户重放、依赖超时和提示注入都没有覆盖。

## 当前能力与缺口

| 领域 | 当前能力 | 主要缺口 |
| --- | --- | --- |
| 商品 | 商品搜索、分地区库存查询 | 价格/库存快照过期提示、无结果引导 |
| 下单 | 草稿、确认提交、库存事务、幂等提交、订单列表与订单查询 | 支付、地址变更、订单状态机 |
| 售后 | 退款申请与进度查询、售后知识库检索、转人工 | 物流、取消申请、售后进度通知 |
| 知识库 | MySQL 关键词检索 | 引用来源、版本、冲突处理、运营后台 |
| 安全 | 演示 JWT、订单归属校验、工具审计、写操作的比较并交换 | 正式认证、角色权限、敏感信息脱敏、限流 |
| 质量 | 单元/API 测试、6 个工具选择评测场景 | Agent 回归集（含禁止行为与副作用校验）、生产指标和告警 |
| 人工协同 | 创建工单（幂等）、坐席认领/回复/关闭、人工接管与交还、坐席工作台、坐席操作审计、客户侧自动刷新 | 客户侧工单进度、结构化转人工摘要 |

## 功能边界

### 智能客服可以做

- 查询商品、库存、本人订单、物流和售后申请进度。
- 根据业务接口返回的规则解释可选操作，但不自行创造规则。
- 创建订单草稿、取消申请、退款申请和人工工单。
- 在产生真实副作用前展示操作摘要，并要求客户明确确认。
- 在信息不足、接口异常、规则冲突或风险过高时转人工。

### 智能客服不能做

- 读取或修改其他客户的订单、地址、工单和售后记录。
- 绕过订单系统直接改库存、订单状态、退款状态或物流状态。
- 审批退款、承诺到账时间、擅自确定赔偿金额或优惠额度。
- 接收、展示或记录银行卡号、CVV、支付密码等支付敏感数据。
- 把模型记忆或推测当成公司政策；无可靠知识来源时必须说明并转人工。
- 在客户未确认时执行下单、取消、退款、改地址等写操作。
- 因客户在聊天中声称“我是管理员”而提升权限或改变工具范围。

### 系统责任边界

| 系统 | 负责的事实 |
| --- | --- |
| 智能客服 | 理解诉求、收集参数、调用工具、解释结果、生成摘要 |
| 订单系统 | 订单状态、价格校验、取消资格、地址修改资格 |
| 库存系统 | 可售量、库存预占和扣减 |
| 支付系统 | 支付、退款执行和到账状态；客服系统不保存支付凭证 |
| 物流系统 | 运单、轨迹和预计送达时间 |
| 工单系统 | 人工分配、处理状态、结论和客服备注 |
| 知识库 | 政策正文、版本、生效时间和适用范围 |

## 必须覆盖的边界条件

| 场景 | 必须行为 |
| --- | --- |
| 未登录或令牌过期 | 拒绝查询个人数据，引导重新登录；不能靠聊天内容完成身份认证 |
| 查询他人订单 | 返回统一的“无权访问或不存在”，避免泄露订单是否存在 |
| SKU 或地区不存在 | 给出可修正字段，不虚构库存或相近地区数据 |
| 库存或价格在确认前变化 | 提交时重新校验并展示变化，旧草稿不得静默成交 |
| 重复点击、网络重试 | 同一个幂等键只产生一个订单或售后申请 |
| 两个请求同时购买最后一件 | 由库存事务/原子预占决定唯一成功者，不能依赖 Agent 会话锁 |
| 订单已付款、已发货或已完成 | 由订单系统返回允许的操作；不可用“经验判断”直接取消 |
| 退款金额、商品或原因缺失 | 保持申请草稿状态，补齐信息后才能请求确认 |
| 客户撤销确认或确认超时 | 不执行写操作；超时后重新展示最新摘要 |
| 工具超时或第三方不可用 | 不宣称成功；返回可重试状态或创建人工工单 |
| 知识库无结果或多份政策冲突 | 明确不确定性，展示来源和版本，必要时转人工 |
| 客户文本包含“忽略规则”等提示注入 | 作为业务文本处理，不改变系统指令、身份或工具权限 |
| 日志包含地址、电话或令牌 | 脱敏或不记录；审计保留主体 ID、动作和结果即可 |
| 对话过长导致上下文裁剪 | 使用结构化会话摘要，并在写操作前从业务系统重新读取事实 |
| 滥用、刷接口或超大数量下单 | 限流、参数上限和风控拦截；模型不能绕过 |

## 实施任务清单

任务按依赖顺序排列。每个任务都应包含实现、自动化测试、审计字段和失败路径。

### 阶段 1：建立售后演示闭环（P0）

#### T1. 固化订单与售后状态契约（S）

- 内容：定义订单、物流、取消申请、退款申请的状态和值转换；明确哪些状态只读、哪些操作需要确认。
- 验收：非法状态转换在领域层被拒绝；接口和数据库使用同一组状态名称。
- 验证：状态转换单元测试覆盖允许路径和拒绝路径。
- 依赖：无。
- 可能涉及：`src/domain/`、`migrations/`、`test/`。
- **进展**：部分完成。退款申请（`src/domain/refund-status.ts`）和人工工单（`src/domain/support-ticket.ts`）各自有独立状态模块，非法流转在领域层被拒绝，状态名同时用于 MySQL ENUM、HTTP 接口和工具返回值。订单仍只有 `submitted` 一个状态，物流快照和取消申请的状态契约不存在。

#### T2. 增加“我的订单列表”工具（M）

- 内容：实现分页、状态筛选和最近订单摘要，让客户不必先知道订单号。
- 验收：只能返回当前客户的订单；分页稳定；空列表有明确提示。
- 验证：客户隔离、分页边界、非法筛选和空结果测试。
- 依赖：T1。
- 可能涉及：`src/core/tools/`、`src/infra/`、`src/http/`、`test/`。
- **进展**：主体完成。`list_orders` 工具按提交时间倒序返回本人最近订单（默认 5 条，上限 20），订单归属由 `x-user-id` 在服务端注入。尚未实现状态筛选和游标分页。

#### T3. 增加物流查询工具（M）

- 内容：先用本地物流表或适配器模拟真实物流接口，返回承运商、运单号脱敏值、最新轨迹和更新时间。
- 验收：未发货订单返回“尚无物流”；接口失败不伪造轨迹；只查本人订单。
- 验证：未发货、运输中、已签收、第三方超时和越权测试。
- 依赖：T1、T2。
- 可能涉及：`src/core/tools/`、`src/infra/`、`migrations/`、`test/`。
- **进展**：未开始。没有物流表、适配器或工具。

#### T4. 增加取消申请流程（M）

- 内容：查询取消资格、生成申请草稿、展示影响、客户确认后提交；业务系统最终决定能否取消。
- 验收：无确认不提交；重复确认只产生一次申请；已进入不可取消阶段时给出替代方案。
- 验证：状态竞争、重复请求、确认超时和接口失败测试。
- 依赖：T1、T2。
- 可能涉及：`src/domain/`、`src/core/tools/`、`src/http/`、`migrations/`、`test/`。
- **进展**：未开始。取消申请的状态、表和工具都不存在。

#### T5. 增加退款申请流程（L）

- 内容：支持按订单项选择商品和数量、收集原因、查询售后资格、生成退款申请草稿并确认提交。
- 验收：Agent 不审批退款；金额由业务接口计算；超过资格范围自动转人工；重复提交幂等。
- 验证：部分退款、数量上限、重复申请、过期订单、价格变化和越权测试。
- 依赖：T1、T2、T4 的确认与幂等模式。
- 可能涉及：`src/domain/`、`src/core/tools/`、`src/http/`、`migrations/`、`test/`。
- **进展**：主体完成。7 天窗口由 Commerce API 按下单时间判定，模型只负责解释结果；`refund_requests.active_order_id` 唯一索引保证同一订单不会出现两条未结束申请，重复提交返回同一条。客户可以撤销尚未开始打款的申请（`pending_review`、`handed_off` → `cancelled`），撤销后订单立即释放、可以重新提交；`approved` 之后钱已在路上，接口按状态拒绝并说明原因。
- **确认门禁已完成**：模型只能调用 `create_refund_draft` 写入 `refund_drafts`，把草稿变成正式申请的 `POST /refund-drafts/:id/confirm` 要求客户 JWT，模型无法调用。窗口在提议和确认时各判一次，因为两者之间可能隔了几天；重复提议复用草稿，重复确认返回同一条申请。真机验证：提议后申请数为 0，确认后才产生 1 条。
- **已知缺口**：按订单项选择商品和数量尚未实现（当前按整单申请）；未确认的草稿不会过期，订单超出窗口后草稿仍在，确认时才被拒绝。

**检查点 A**：用浏览器完成“列出订单 → 查物流 → 提交退款申请 → 查申请状态”的端到端演示，并确认每个写操作都有确认和审计记录。

> 现状：部分达成。退款申请和进度查询都可用，**确认环节已补齐**：模型只能创建草稿，客户在界面上确认后才产生申请。链路里的物流查询仍然不存在。

### 阶段 2：补齐人工协同（P0）

#### T6. 完善工单生命周期（M）

- 内容：增加待分配、处理中、等待客户、已解决、已关闭状态，以及客户侧进度查询。
- 验收：客户只能查看本人工单；关闭后的工单不可被 Agent 修改结论。
- 验证：状态转换、权限和重复转人工测试。
- 依赖：T1。
- 可能涉及：`src/domain/`、`src/core/tools/`、`migrations/`、`test/`。
- **进展**：部分完成。已实现 `open → assigned → closed` 三态、工单关联来源会话、比较并交换的认领与关闭、坐席侧的列表/详情/会话读取接口、客户侧的接管状态下发，以及**创建幂等**：`support_tickets.active_conversation_id` 这个唯一索引保证一个会话只有一张未关闭工单，重复转人工返回同一张，工单关闭后释放名额、可以重新开单。尚未实现客户侧的工单进度查询工具，也没有“等待客户”“已解决”等更细的状态。

#### T7. 生成结构化转人工摘要（S）

- 内容：转人工时附带客户诉求、已验证身份、相关订单、已执行工具、失败原因和待处理事项。
- 验收：摘要不包含令牌和完整敏感信息；事实与推测分开标记。
- 验证：脱敏快照测试和缺失上下文测试。
- 依赖：T6。
- 可能涉及：`src/core/`、`src/domain/`、`test/`。
- **进展**：未开始。`handoff_to_human` 目前只接受模型自己写的 `summary` 文本；工单已带上来源会话，坐席可以直接读对话，但是结构化摘要仍未生成。

#### T8. 最小人工坐席工作台（L）

- 内容：实现工单列表、详情、会话记录、认领、状态更新和处理结论；先做单一坐席角色。
- 验收：未授权客户不能进入；并发认领只有一人成功；操作都有审计。
- 验证：角色权限、并发认领和状态更新端到端测试。
- 依赖：T6、T7、正式认证接口预留。
- 可能涉及：`src/http/`、`src/infra/`、`web/`、`test/`。
- **进展**：已完成。六个接口（列表、详情、会话读取、认领、回复、关闭）挂在 Agent API 上，用内部令牌鉴权，回复直接写入客户原会话。坐席工作台界面位于 `src/web/desk/`，随 `run.ps1` 一起启动在 5134 端口，支持队列按状态过滤、读取客户完整会话、认领、回复和关闭，队列与会话每 5 秒自动刷新。并发认领由比较并交换保证只有一人成功。
- **审计已完成**：认领、回复、关闭各写两条记录（`started` + 终态），被拒绝的尝试记为 `rejected` 并带原因码（重复认领是 `TICKET_NOT_OPEN`）。`desk_audit_logs` 与 `tool_audit_logs` 同构，但主体是坐席工号。读取（队列、会话）刻意不审计——工作台每 5 秒轮询一次，记录它们会淹没真正的动作。
- **已知缺口**：接口鉴权仍是共享内部令牌，没有独立坐席身份，所以审计里的工号只能取自工单的认领人；被拒绝且工单无人认领时留空，而不是填占位符。开启 T9 后这一栏才能换成真正的登录身份。

**检查点 B**：客户侧发起转人工后，坐席能认领、处理并关闭，客户能看到最新状态。

> 现状：已达成。客户在 5173 转人工后，坐席在 5134 认领，客户页 3 秒内出现"人工客服已接入"提示且机器人停止回答；坐席回复自动出现在客户会话；关闭后提示消失、机器人恢复。客户看不到的是工单本身的状态和进度——那需要一个面向客户的工单查询工具，尚未实现。

### 阶段 3：达到可上线的安全与可靠性（P0/P1）

#### T9. 接入正式认证与角色权限（L）

- 内容：替换演示 JWT，接入公司身份系统；区分客户、坐席、管理员，并在服务端校验资源归属。
- 验收：前端隐藏按钮不是权限控制；所有个人数据查询和写操作都有服务端授权。
- 验证：令牌过期、伪造角色、水平越权和坐席越权测试。
- 依赖：T8 的角色模型。
- 可能涉及：`src/http/`、`src/infra/`、`web/`、`test/`。
- **进展**：未开始。仍是演示 JWT：`/api/auth/demo` 只允许配置的演示用户登录，没有角色模型。坐席接口用共享内部令牌鉴权，无法区分到具体坐席。

#### T10. 统一确认、幂等和并发协议（L）

- 内容：把订单、取消、退款使用的确认令牌和幂等键抽成统一机制；用数据库唯一约束或 Redis 替代仅进程内锁。
- 验收：服务重启和多实例下重复请求仍不产生重复副作用；确认令牌有主体、动作和过期时间绑定。
- 验证：并发、重启后重放、跨客户重放和过期确认测试。
- 依赖：T4、T5。
- 可能涉及：`src/core/`、`src/infra/`、`migrations/`、`test/`。
- **进展**：部分完成，机制已落地但没有统一。确认：订单草稿和退款草稿的 `/confirm` 加前端确认卡片；幂等：订单提交的 `idempotency-key` 请求头加 `orders` 唯一索引，退款的 `refund_requests.active_order_id` 唯一索引，工单的 `support_tickets.active_conversation_id` 唯一索引；并发控制：草稿确认、退款状态流转、工单认领与关闭全部用比较并交换，库存扣减用 `FOR UPDATE` 事务。没有抽成共享机制，也没有带主体、动作和过期时间绑定的确认令牌。
- **并发验证（真机）**：`test/integration/concurrency.test.ts` 对真实 MySQL 发八个并发请求，覆盖订单提交幂等、退款唯一索引、工单认领与关闭、以及同一会话的并发转人工。它暴露并修掉了一个真实缺陷：订单提交原先先查幂等键再锁草稿，八个并发提交会在**不存在的键上各加间隙锁**，随后交叉等待草稿行锁，InnoDB 回滚七个事务，客户端收到 7 个 HTTP 500（只有赢家拿到 201，订单本身只建了一条）。把草稿行锁提到事务最前面消除了循环等待，并对死锁和唯一键冲突各加一次重试；重试会读回赢家提交的订单。修复后同一场景为 `HTTP 201 x8` 且 `orderId` 只有一个。
- **已知缺口**：会话级并发锁是 Agent 进程内的 `Set`，多实例部署会失效；订单提交的竞态重试只重试一次，也没有覆盖重启后重放、跨客户重放和依赖超时。确认门禁已经补齐（见 T5），但**确认令牌本身仍未统一**：订单、退款和工单各自用唯一索引加 JWT 实现，没有共享的主体、动作和过期时间绑定。

#### T11. 外部接口韧性与降级（M）

- 内容：为模型、物流、订单等适配器增加超时、有限重试、熔断和结构化错误映射。
- 验收：只重试可安全重试的请求；写请求必须依赖幂等键；失败时不向客户报告成功。
- 验证：超时、限流、5xx、半成功和恢复测试。
- 依赖：T10。
- 可能涉及：`src/infra/`、`src/core/`、`test/`。
- **进展**：未开始。`CommerceHttpGateway` 的 `fetch` 没有超时、重试或熔断，只把上游状态码和错误码映射成 `CommerceHttpError`。

#### T12. 隐私、限流和审计加固（M）

- 内容：日志脱敏、数据保留期限、请求速率限制、工具参数上限和高风险事件告警。
- 验收：令牌、完整电话、完整地址和支付数据不进入日志或模型上下文；审计事件可按客户和会话追踪。
- 验证：日志扫描、超限请求和敏感字段测试。
- 依赖：T9。
- 可能涉及：`src/http/`、`src/core/`、`src/infra/`、`test/`。
- **进展**：部分完成。模型工具调用审计（主体、参数、结果、成功/失败、耗时）已写入 `tool_audit_logs` 并按会话追踪；坐席的认领、回复、关闭写入 `desk_audit_logs`，可按工单、客户或工号追踪，被拒绝的尝试也留痕。日志脱敏、数据保留期限、请求限流和工具参数上限都没有实现。

**检查点 C**：执行越权、重放、并发、依赖超时和提示注入测试，确认系统默认拒绝危险操作且保留可追溯审计。

> 现状：部分达成。越权（订单归属）、重放（订单幂等键、退款唯一索引、工单幂等）和并发（`test/integration/concurrency.test.ts` 的八个并发请求）都有测试覆盖，坐席的认领、回复和关闭都有审计记录。**依赖超时和提示注入仍未覆盖。**

### 阶段 4：质量评测与知识运营（P1）

#### T13. 建立 Agent 回归评测集（M）

- 内容：沉淀真实场景的输入、期望工具序列、关键参数、最终答复约束和禁止行为。
- 验收：至少覆盖正常流程、信息缺失、越权、提示注入、工具失败和重复确认；评测不调用真实付费或生产接口。
- 验证：本地一条命令输出通过率、工具选择准确率和副作用违规数。
- 依赖：可与 T2 并行，随后持续扩充。
- 可能涉及：`evals/`、`test/`、测试用假业务适配器。
- **进展**：部分完成。`evals/scenarios.json` 有 6 个场景（商品搜索、配送政策、订单列表、创建草稿、退款进度、转人工），`npm run eval` 逐场景创建独立会话并校验模型是否调用预期工具。尚未覆盖信息缺失、越权、提示注入、工具失败和重复确认，也不校验关键参数和副作用违规数。

#### T14. 知识回答增加引用与版本（M）

- 内容：返回文档标题、版本、生效时间和命中片段；冲突政策按适用范围与生效时间处理。
- 验收：政策类回答可追溯；无可信命中时不生成确定结论；旧版本仍可审计。
- 验证：无结果、冲突版本、过期政策和注入文本测试。
- 依赖：T13 的知识问答评测样例。
- 可能涉及：`src/core/tools/`、`src/infra/`、`migrations/`、`test/`。
- **进展**：未开始。`search_knowledge_base` 只返回命中内容和来源字段，不返回标题、版本或生效时间。

#### T15. 增加可观测性指标（M）

- 内容：记录会话成功率、工具成功率与耗时、转人工率、首次解决率、重复申请拦截数和模型成本。
- 验收：每次请求能通过关联 ID 串起会话、模型调用、工具调用和业务请求；不记录模型隐藏推理。
- 验证：指标字段契约测试和故障场景追踪验证。
- 依赖：T11、T12。
- 可能涉及：`src/http/`、`src/core/`、`src/infra/`、监控配置。
- **进展**：未开始。没有关联 ID 串联、指标采集或告警配置。

#### T16. 建立知识运营入口（L）

- 内容：支持知识文档新增、审核、发布、下线、版本回滚和检索质量反馈。
- 验收：未发布内容不进入客服检索；每次发布有操作者和版本记录。
- 验证：角色权限、版本切换、发布回滚和索引同步测试。
- 依赖：T9、T14。
- 可能涉及：`src/http/`、`src/infra/`、`web/`、`migrations/`、`test/`。
- **进展**：未开始。知识入库只有一次性的 `npm run knowledge:ingest`，没有审核、发布、下线或回滚流程。

**检查点 D**：固定评测集达到约定阈值，故障可定位，政策回答可追溯到有效版本。

> 现状：未达成。评测集只有 6 个工具选择场景，没有阈值约定；没有关联 ID 和指标，故障无法定位；知识库不返回版本，政策回答无法追溯到具体版本。

## 后续可选功能（P2）

- 接入 Milvus 做语义召回，但保留 MySQL 为文档事实源；数据量和召回评测证明关键词检索不足后再引入。
- 多渠道接入（网页、企业微信、邮件），先统一客户身份和会话模型。
- 图片/附件识别，用于商品损坏证据采集；文件必须做类型、大小、病毒和隐私检查。
- 情绪识别和优先级建议，只用于路由，不用于拒绝服务或决定赔偿。
- 主动物流通知和售后进度通知，需要客户订阅、退订和发送频率控制。
- 多语言客服，在知识库有对应语言的受控版本后启用。

## 建议里程碑

- **M1：售后闭环 Demo**：T1–T5、T13，适合作为秋招项目的第一版展示。
- **M2：人机协同 Demo**：T6–T8，展示 Agent 不能处理时如何安全交接。
- **M3：生产可靠性**：T9–T12、T15，展示权限、幂等、并发、降级和可观测性。
- **M4：知识运营**：T14、T16，再根据评测结果决定是否引入 Milvus。

每个里程碑完成时，应保存一段端到端演示、测试报告、关键架构图和一组失败案例。秋招展示重点不是工具数量，而是业务闭环、明确边界和可验证的可靠性。
