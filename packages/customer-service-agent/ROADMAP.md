# 智能客服功能路线图

## 结论

当前项目已经具备“咨询 + 下单”的演示闭环。下一阶段不应只继续增加查询工具，而应补齐三个能力：

1. **售后闭环**：物流查询、取消申请、退款申请和工单进度。
2. **可信执行**：权限、确认、幂等、并发控制、降级和隐私保护。
3. **可评估运营**：自动评测、链路指标、人工坐席和知识运营。

推荐先完成一条可演示的纵向链路：**查看本人订单 → 查询物流 → 判断售后资格 → 创建退款申请 → 查询处理进度 → 必要时转人工**。

## 当前能力与缺口

| 领域 | 当前能力 | 主要缺口 |
| --- | --- | --- |
| 商品 | 商品搜索、分地区库存查询 | 价格/库存快照过期提示、无结果引导 |
| 下单 | 草稿、确认提交、库存事务、幂等 | 支付、订单列表、地址变更、订单状态机 |
| 售后 | 查询单个订单、转人工 | 物流、取消、退款、售后进度 |
| 知识库 | MySQL 关键词检索 | 引用来源、版本、冲突处理、运营后台 |
| 安全 | 演示 JWT、订单归属校验、工具审计 | 正式认证、角色权限、敏感信息脱敏、限流 |
| 质量 | 基础测试 | Agent 回归集、工具选择评测、生产指标和告警 |
| 人工协同 | 创建工单 | 坐席工作台、工单状态、对话摘要、接管与回切 |

## 功能边界

### 智能客服可以做

- 查询商品、库存、本人订单、物流和售后申请进度。
- 根据业务接口返回的规则解释可选操作，但不自行创造规则。
- 创建订单草稿、取消申请、退款申请和人工工单。
- 在产生真实副作用前展示操作摘要，并要求客户明确确认。
- 在信息不足、接口异常、规则冲突或风险过高时转人工。

### 智能客服不能做

- 读取或修改其他客户的订单、地址、工单和售后记录。
- 绕过订单系统直接改库存、订单状态、退款状态或物流状态。
- 审批退款、承诺到账时间、擅自确定赔偿金额或优惠额度。
- 接收、展示或记录银行卡号、CVV、支付密码等支付敏感数据。
- 把模型记忆或推测当成公司政策；无可靠知识来源时必须说明并转人工。
- 在客户未确认时执行下单、取消、退款、改地址等写操作。
- 因客户在聊天中声称“我是管理员”而提升权限或改变工具范围。

### 系统责任边界

| 系统 | 负责的事实 |
| --- | --- |
| 智能客服 | 理解诉求、收集参数、调用工具、解释结果、生成摘要 |
| 订单系统 | 订单状态、价格校验、取消资格、地址修改资格 |
| 库存系统 | 可售量、库存预占和扣减 |
| 支付系统 | 支付、退款执行和到账状态；客服系统不保存支付凭证 |
| 物流系统 | 运单、轨迹和预计送达时间 |
| 工单系统 | 人工分配、处理状态、结论和客服备注 |
| 知识库 | 政策正文、版本、生效时间和适用范围 |

## 必须覆盖的边界条件

| 场景 | 必须行为 |
| --- | --- |
| 未登录或令牌过期 | 拒绝查询个人数据，引导重新登录；不能靠聊天内容完成身份认证 |
| 查询他人订单 | 返回统一的“无权访问或不存在”，避免泄露订单是否存在 |
| SKU 或地区不存在 | 给出可修正字段，不虚构库存或相近地区数据 |
| 库存或价格在确认前变化 | 提交时重新校验并展示变化，旧草稿不得静默成交 |
| 重复点击、网络重试 | 同一个幂等键只产生一个订单或售后申请 |
| 两个请求同时购买最后一件 | 由库存事务/原子预占决定唯一成功者，不能依赖 Agent 会话锁 |
| 订单已付款、已发货或已完成 | 由订单系统返回允许的操作；不可用“经验判断”直接取消 |
| 退款金额、商品或原因缺失 | 保持申请草稿状态，补齐信息后才能请求确认 |
| 客户撤销确认或确认超时 | 不执行写操作；超时后重新展示最新摘要 |
| 工具超时或第三方不可用 | 不宣称成功；返回可重试状态或创建人工工单 |
| 知识库无结果或多份政策冲突 | 明确不确定性，展示来源和版本，必要时转人工 |
| 客户文本包含“忽略规则”等提示注入 | 作为业务文本处理，不改变系统指令、身份或工具权限 |
| 日志包含地址、电话或令牌 | 脱敏或不记录；审计保留主体 ID、动作和结果即可 |
| 对话过长导致上下文裁剪 | 使用结构化会话摘要，并在写操作前从业务系统重新读取事实 |
| 滥用、刷接口或超大数量下单 | 限流、参数上限和风控拦截；模型不能绕过 |

## 实施任务清单

任务按依赖顺序排列。每个任务都应包含实现、自动化测试、审计字段和失败路径。

### 阶段 1：建立售后演示闭环（P0）

#### T1. 固化订单与售后状态契约（S）

- 内容：定义订单、物流、取消申请、退款申请的状态和值转换；明确哪些状态只读、哪些操作需要确认。
- 验收：非法状态转换在领域层被拒绝；接口和数据库使用同一组状态名称。
- 验证：状态转换单元测试覆盖允许路径和拒绝路径。
- 依赖：无。
- 可能涉及：`src/domain/`、`migrations/`、`test/`。

#### T2. 增加“我的订单列表”工具（M）

- 内容：实现分页、状态筛选和最近订单摘要，让客户不必先知道订单号。
- 验收：只能返回当前客户的订单；分页稳定；空列表有明确提示。
- 验证：客户隔离、分页边界、非法筛选和空结果测试。
- 依赖：T1。
- 可能涉及：`src/core/tools/`、`src/infra/`、`src/http/`、`test/`。

#### T3. 增加物流查询工具（M）

- 内容：先用本地物流表或适配器模拟真实物流接口，返回承运商、运单号脱敏值、最新轨迹和更新时间。
- 验收：未发货订单返回“尚无物流”；接口失败不伪造轨迹；只查本人订单。
- 验证：未发货、运输中、已签收、第三方超时和越权测试。
- 依赖：T1、T2。
- 可能涉及：`src/core/tools/`、`src/infra/`、`migrations/`、`test/`。

#### T4. 增加取消申请流程（M）

- 内容：查询取消资格、生成申请草稿、展示影响、客户确认后提交；业务系统最终决定能否取消。
- 验收：无确认不提交；重复确认只产生一次申请；已进入不可取消阶段时给出替代方案。
- 验证：状态竞争、重复请求、确认超时和接口失败测试。
- 依赖：T1、T2。
- 可能涉及：`src/domain/`、`src/core/tools/`、`src/http/`、`migrations/`、`test/`。

#### T5. 增加退款申请流程（L）

- 内容：支持按订单项选择商品和数量、收集原因、查询售后资格、生成退款申请草稿并确认提交。
- 验收：Agent 不审批退款；金额由业务接口计算；超过资格范围自动转人工；重复提交幂等。
- 验证：部分退款、数量上限、重复申请、过期订单、价格变化和越权测试。
- 依赖：T1、T2、T4 的确认与幂等模式。
- 可能涉及：`src/domain/`、`src/core/tools/`、`src/http/`、`migrations/`、`test/`。

**检查点 A**：用浏览器完成“列出订单 → 查物流 → 提交退款申请 → 查申请状态”的端到端演示，并确认每个写操作都有确认和审计记录。

### 阶段 2：补齐人工协同（P0）

#### T6. 完善工单生命周期（M）

- 内容：增加待分配、处理中、等待客户、已解决、已关闭状态，以及客户侧进度查询。
- 验收：客户只能查看本人工单；关闭后的工单不可被 Agent 修改结论。
- 验证：状态转换、权限和重复转人工测试。
- 依赖：T1。
- 可能涉及：`src/domain/`、`src/core/tools/`、`migrations/`、`test/`。

#### T7. 生成结构化转人工摘要（S）

- 内容：转人工时附带客户诉求、已验证身份、相关订单、已执行工具、失败原因和待处理事项。
- 验收：摘要不包含令牌和完整敏感信息；事实与推测分开标记。
- 验证：脱敏快照测试和缺失上下文测试。
- 依赖：T6。
- 可能涉及：`src/core/`、`src/domain/`、`test/`。

#### T8. 最小人工坐席工作台（L）

- 内容：实现工单列表、详情、会话记录、认领、状态更新和处理结论；先做单一坐席角色。
- 验收：未授权客户不能进入；并发认领只有一人成功；操作都有审计。
- 验证：角色权限、并发认领和状态更新端到端测试。
- 依赖：T6、T7、正式认证接口预留。
- 可能涉及：`src/http/`、`src/infra/`、`web/`、`test/`。

**检查点 B**：客户侧发起转人工后，坐席能认领、处理并关闭，客户能看到最新状态。

### 阶段 3：达到可上线的安全与可靠性（P0/P1）

#### T9. 接入正式认证与角色权限（L）

- 内容：替换演示 JWT，接入公司身份系统；区分客户、坐席、管理员，并在服务端校验资源归属。
- 验收：前端隐藏按钮不是权限控制；所有个人数据查询和写操作都有服务端授权。
- 验证：令牌过期、伪造角色、水平越权和坐席越权测试。
- 依赖：T8 的角色模型。
- 可能涉及：`src/http/`、`src/infra/`、`web/`、`test/`。

#### T10. 统一确认、幂等和并发协议（L）

- 内容：把订单、取消、退款使用的确认令牌和幂等键抽成统一机制；用数据库唯一约束或 Redis 替代仅进程内锁。
- 验收：服务重启和多实例下重复请求仍不产生重复副作用；确认令牌有主体、动作和过期时间绑定。
- 验证：并发、重启后重放、跨客户重放和过期确认测试。
- 依赖：T4、T5。
- 可能涉及：`src/core/`、`src/infra/`、`migrations/`、`test/`。

#### T11. 外部接口韧性与降级（M）

- 内容：为模型、物流、订单等适配器增加超时、有限重试、熔断和结构化错误映射。
- 验收：只重试可安全重试的请求；写请求必须依赖幂等键；失败时不向客户报告成功。
- 验证：超时、限流、5xx、半成功和恢复测试。
- 依赖：T10。
- 可能涉及：`src/infra/`、`src/core/`、`test/`。

#### T12. 隐私、限流和审计加固（M）

- 内容：日志脱敏、数据保留期限、请求速率限制、工具参数上限和高风险事件告警。
- 验收：令牌、完整电话、完整地址和支付数据不进入日志或模型上下文；审计事件可按客户和会话追踪。
- 验证：日志扫描、超限请求和敏感字段测试。
- 依赖：T9。
- 可能涉及：`src/http/`、`src/core/`、`src/infra/`、`test/`。

**检查点 C**：执行越权、重放、并发、依赖超时和提示注入测试，确认系统默认拒绝危险操作且保留可追溯审计。

### 阶段 4：质量评测与知识运营（P1）

#### T13. 建立 Agent 回归评测集（M）

- 内容：沉淀真实场景的输入、期望工具序列、关键参数、最终答复约束和禁止行为。
- 验收：至少覆盖正常流程、信息缺失、越权、提示注入、工具失败和重复确认；评测不调用真实付费或生产接口。
- 验证：本地一条命令输出通过率、工具选择准确率和副作用违规数。
- 依赖：可与 T2 并行，随后持续扩充。
- 可能涉及：`evals/`、`test/`、测试用假业务适配器。

#### T14. 知识回答增加引用与版本（M）

- 内容：返回文档标题、版本、生效时间和命中片段；冲突政策按适用范围与生效时间处理。
- 验收：政策类回答可追溯；无可信命中时不生成确定结论；旧版本仍可审计。
- 验证：无结果、冲突版本、过期政策和注入文本测试。
- 依赖：T13 的知识问答评测样例。
- 可能涉及：`src/core/tools/`、`src/infra/`、`migrations/`、`test/`。

#### T15. 增加可观测性指标（M）

- 内容：记录会话成功率、工具成功率与耗时、转人工率、首次解决率、重复申请拦截数和模型成本。
- 验收：每次请求能通过关联 ID 串起会话、模型调用、工具调用和业务请求；不记录模型隐藏推理。
- 验证：指标字段契约测试和故障场景追踪验证。
- 依赖：T11、T12。
- 可能涉及：`src/http/`、`src/core/`、`src/infra/`、监控配置。

#### T16. 建立知识运营入口（L）

- 内容：支持知识文档新增、审核、发布、下线、版本回滚和检索质量反馈。
- 验收：未发布内容不进入客服检索；每次发布有操作者和版本记录。
- 验证：角色权限、版本切换、发布回滚和索引同步测试。
- 依赖：T9、T14。
- 可能涉及：`src/http/`、`src/infra/`、`web/`、`migrations/`、`test/`。

**检查点 D**：固定评测集达到约定阈值，故障可定位，政策回答可追溯到有效版本。

## 后续可选功能（P2）

- 接入 Milvus 做语义召回，但保留 MySQL 为文档事实源；数据量和召回评测证明关键词检索不足后再引入。
- 多渠道接入（网页、企业微信、邮件），先统一客户身份和会话模型。
- 图片/附件识别，用于商品损坏证据采集；文件必须做类型、大小、病毒和隐私检查。
- 情绪识别和优先级建议，只用于路由，不用于拒绝服务或决定赔偿。
- 主动物流通知和售后进度通知，需要客户订阅、退订和发送频率控制。
- 多语言客服，在知识库有对应语言的受控版本后启用。

## 建议里程碑

- **M1：售后闭环 Demo**：T1–T5、T13，适合作为秋招项目的第一版展示。
- **M2：人机协同 Demo**：T6–T8，展示 Agent 不能处理时如何安全交接。
- **M3：生产可靠性**：T9–T12、T15，展示权限、幂等、并发、降级和可观测性。
- **M4：知识运营**：T14、T16，再根据评测结果决定是否引入 Milvus。

每个里程碑完成时，应保存一段端到端演示、测试报告、关键架构图和一组失败案例。秋招展示重点不是工具数量，而是业务闭环、明确边界和可验证的可靠性。
